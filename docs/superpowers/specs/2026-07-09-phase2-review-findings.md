## Reviewer 1 — 12 findings

### [blocker] published_summaries.last_refreshed is a friend-readable last_active timestamp
- **File:** supabase/schema.sql:1353
- **Detail:** Spec §0.3 (invariant 3) requires the projection to contain NO field that lets a friend infer inactivity: 'không last_good_date, không last_active'. `last_refreshed timestamptz` is updated to now() on every refresh_my_summary call (wired to pet switch and display-name save, intended to run after every sync flush), and the friends RLS SELECT policy exposes the whole row. getFriendSummary (src/lib/server/social-actions.ts:604) even selects it explicitly and ships it to the visiting friend's browser as PublishedSummary.lastRefreshed. Concrete failure: Lan opens Mai's garden overlay twice a week; lastRefreshed stops advancing on July 1 → Lan knows exactly when Mai went dark. 'A friend going dark is invisible' is structurally broken.
- **Suggested fix:** Remove last_refreshed from the friend-readable surface: either drop the column (server can use updated_at guarded by column-level privileges), or use Postgres column grants / a security-barrier view so friends can only SELECT the whitelisted projection columns; strip lastRefreshed from PublishedSummary and the .select() list.

### [blocker] current_streak/best_streak in the projection let friends compute the host's last miss day
- **File:** supabase/schema.sql:1350
- **Detail:** Spec §4.1 deliberately enumerates the summary fields (rhythm_score, fair-gated weekly_good_days, pet fields, milestones) and contains no streak fields, precisely because a current streak is an inverted miss-counter: currentStreak = N means the host's last miss was exactly N+1 days ago. The overlay renders it to visitors as '🔥 N ngày liền tay' (garden-visit-overlay.tsx:262). Concrete failure: Mai returns after a week away, her client calls refresh_my_summary → every friend watches her badge collapse from '🔥 15 ngày liền tay' to nothing/1 — the comeback moment (the exact Strava-lesson scenario in §9) is publicly surfaced as a fall. best_streak additionally lets friends see best>current ('she fell from her best').
- **Suggested fix:** Drop current_streak and best_streak from published_summaries, the RPC, PublishedSummary, and the overlay badge. If a positive activity signal is wanted, implement the spec's rhythm_score / fair_opt_in-gated weekly_good_days (0–7 cap) instead.

### [blocker] Gift unique index has no kind filter — any second same-day interaction with a friend errors, masked as a network problem
- **File:** supabase/schema.sql:1483
- **Detail:** garden_visits_one_gift_per_host_visitor_date is defined on (host_user_id, visitor_user_id, visit_date) WHERE applied_at IS NULL with no gifted_food/kind predicate, but visit_garden inserts a pending row for EVERY action (pet, gift, cheer). Concrete failure: visitor taps 'Vuốt ve' (row inserted), then taps 'Vuốt ve' again or 'Tặng món ăn' → unique violation → whole transaction rolls back → overlay's handlePet/handleGift fall through to toast('Mạng hơi chập chờn — Sếp thử lại sau chút nha ☁️'). Petting a friend's pet twice — the most natural interaction — becomes an error dressed up as a network lie, and gifting after petting is impossible until the host acks. Spec §4.2 requires over-cap petting to stay 'animation + thoại, không tạo record' — affection must never error. Spec's index is scoped `where (kind = 'gift')` and NOT filtered on applied/pending, so the built version also re-opens the 1-gift/day cap as soon as the host acks.
- **Suggested fix:** Scope the index to gifts only and drop the applied_at predicate: `on garden_visits (host_user_id, visitor_user_id, visit_date) where gifted_food = 1`. In the RPC, make over-cap pet actions return ok-without-insert instead of raising.

### [blocker] No write path for sharing_enabled or profiles.milestones — every garden renders permanently closed
- **File:** supabase/schema.sql:1259
- **Detail:** profiles.sharing_enabled defaults false, update_my_profile(p_display_name, p_avatar_kind) has no sharing parameter, and no UI toggle exists anywhere in src/. refresh_my_summary therefore always takes the `if not v_sharing_enabled` branch (schema.sql:1542) and never publishes a row, and visit_garden always raises 'host-not-sharing'. Likewise nothing in the codebase ever writes profiles.milestones (grep: only schema, types, and reads), so milestones are permanently [] and the entire cheer surface is unreachable. Concrete failure: two real users friend each other, both tap 'Thăm vườn 🏡' → both see 'Vườn đang khép cổng nghỉ ngơi — mình ghé lại lần sau nha 🌿' forever. The whole Phase 2 surface is dead on arrival.
- **Suggested fix:** Add an explicit opt-in toggle (spec §0.4: 'chia sẻ là opt-in riêng') that updates sharing_enabled and immediately calls refresh_my_summary; make refresh_my_summary itself compute/diff milestones server-side (see next finding) instead of reading a never-written profiles column.

### [major] Silent opt-out is client-driven, not structural — a disabled summary stays friend-readable indefinitely
- **File:** supabase/schema.sql:1542
- **Detail:** The only code that deletes a published summary on opt-out is inside refresh_my_summary, which the owner's client must happen to call. The friends SELECT policy on published_summaries checks only friendship, not profiles.sharing_enabled, and there is no trigger backstop (spec §4.1 explicitly prescribes a profiles trigger pattern; §4.1 'tắt → xóa row' at write time). Concrete failure: user sets sharing_enabled=false (via PostgREST today, or a future toggle that fires the RPC but the request drops offline) and closes the app → friends keep SELECTing the full summary (pet, streaks, milestones) for days/weeks until the owner next switches pets or renames themselves. Opt-out is supposed to be immediate and silent; here it is eventually-maybe.
- **Suggested fix:** Add an AFTER UPDATE OF sharing_enabled trigger on profiles that deletes the published_summaries row when it flips false (and/or add `and exists (select 1 from profiles p where p.user_id = published_summaries.user_id and p.sharing_enabled)` to the friends SELECT policy as a second layer).

### [major] Milestones are client-authored free text, not server-diffed — positive-only becomes tonal instead of structural
- **File:** supabase/schema.sql:1335
- **Detail:** Spec §4.1: refresh_my_summary must 'tự append milestones bằng cách diff với row trước (client không bao giờ cung cấp nội dung milestone)'. The build instead copies profiles.milestones — an owner-writable jsonb column — verbatim into the friend-facing projection. The validate_milestones trigger checks only shape/kind/size; `value` is an arbitrary string up to ~200 bytes that every visiting friend renders in the overlay chips (garden-visit-overlay.tsx:356). Concrete failure: any client bug or a user hand-calling PostgREST can publish milestone value 'Lan lười quá, thua mình 10 ngày 😏' — guilt/comparison text delivered through the one surface guaranteed to be 'chỉ điều tích cực'. The invariant is supposed to hold structurally (§0.3), not by trusting the writer. The kind vocabulary ('streak','bond','garden') also diverges from spec ('evolve','bond_tier','bloom_week','new_pet'), and a 'streak' milestone invites streak-number content the projection was designed to exclude.
- **Suggested fix:** Drop profiles.milestones. Have refresh_my_summary derive milestone entries itself (diff pet stage/bond tier/new-pet against the previous published_summaries row) with server-composed, fixed-vocabulary content; clients supply nothing.

### [major] Cheer uniqueness omits visitor_id — only one friend ever can cheer a milestone, others get silent fake success
- **File:** supabase/schema.sql:1487
- **Detail:** garden_visits_one_cheer_per_milestone is on (host_user_id, cheered_milestone_id); spec §4.2 defines it as (visitor_id, host_id, milestoneId) — 1 per milestone PER VISITOR. Concrete failure: Lan cheers Mai's 'bloom' milestone; Hoa later opens Mai's garden and taps the same chip → unique violation → handleCheer's /duplicate|unique/ branch (garden-visit-overlay.tsx:200) silently paints the chip as cheered with no toast — Hoa believes her congratulation was delivered, Mai never receives it. A celebration that silently evaporates while showing success breaks the cheer mechanic for everyone but the first friend.
- **Suggested fix:** Add visitor_user_id to the unique index: `on garden_visits (visitor_user_id, host_user_id, cheered_milestone_id) where cheered_milestone_id is not null`.

### [major] Gift food check only counts TODAY's ledger — yesterday's food triggers 'basket empty' blame toast
- **File:** supabase/schema.sql:1750
- **Detail:** visit_garden computes v_food_balance as today's granted + today's gift-keys − today's spent, ignoring food_carryover and every prior day (spec §2.3 formula: clamp(carryover + Σgranted + Σgifts − Σ|spent|, 0, CAP)). Concrete failure: user earns 3 food Monday, opens a friend's garden Tuesday morning before ticking anything; local myFood=3 so the button is enabled → RPC raises 'insufficient-food' → overlay toasts 'Giỏ đồ ăn của Sếp đang trống — chăm vườn mình chút rồi quay lại nha 🌱' while their basket visibly shows 3. The message contradicts what they see and reads as 'you haven't been tending your garden' — a scolding delivered to someone who did the work. (It also structurally blocks the spec's morning-gift flow.)
- **Suggested fix:** Implement the full ledger formula in the RPC (sum all granted dates + all gift keys + carryover − all spent events, clamped), matching client deriveFoodBalance.

### [major] Host's pet greets the visitor with owner-intimacy 'idle' lines keyed by the visitor's own bond tier
- **File:** src/components/dashboard/garden-visit-overlay.tsx:129
- **Detail:** The greeting uses getPetLine(hostPet.species, myBondTier, "idle") — owner-facing voice lines spoken to a guest, flavored by how bonded the GUEST is with their OWN pet. Spec §7 is explicit that guest-side voice is keyed by species only ('khách không có bond tier với pet nhà người khác') and defines only guestPet/guestGift events. Concrete failure: a fruit-tier visitor enters a near-stranger friend's garden → the host's dog says 'Người nhà ở cạnh nhau vậy thôi là đủ rồi, gâu~' (calls the guest 'family') or 'Sếp bận thì em nằm đây hóng gió chờ Sếp nè' (addresses the guest as its owner, 'Sếp'). False intimacy and misaddressed ownership break the pet-personality brand fiction the whole surface is built on.
- **Suggested fix:** Add a species-keyed guestGreeting event to GUEST_VOICE (or reuse a neutral guestPet line) and stop passing myBondTier into the host-pet greeting.

### [minor] 'Pet cap' counts pending visits of every kind across all hosts and resets on ack
- **File:** supabase/schema.sql:1740
- **Detail:** The 3/day cap counts all garden_visits rows for the visitor today WHERE applied_at IS NULL — gifts and cheers included, across every host, and rows leave the count the moment a host acks. Spec §4.2 defines it as pet-kind only, per (visitor, host)/day, mirroring PETTING_CAP_PER_DAY. Concrete failure: visitor gifts friends A, B, C (3 pending rows), then opens friend D's garden with a full basket and taps 'Tặng món ăn' → 'pet-cap-reached' → handleGift has no branch for it and toasts the network-flaky line; the user retries against a phantom network problem. Conversely, once hosts ack, the same visitor can pet the same host far more than 3 times a day.
- **Suggested fix:** Count only pet-kind rows for (visitor_user_id, host_user_id, visit_date) regardless of applied_at, and only when the action is a pet; return ok-without-record over cap per spec.

### [minor] Cats aged 7–29 growth days are published as 'kitten' — friend sees a baby instead of a junior pet
- **File:** supabase/schema.sql:1564
- **Detail:** Stage derivation: `elsif growth_days <= 29 then case when species = 'dog' then 'junior' else 'kitten' end` — the cat arm of the middle band repeats 'kitten', so a cat is baby-equivalent until day 30. The overlay maps kitten→baby (SUMMARY_STAGE, garden-visit-overlay.tsx:43). Concrete failure: Mai's 20-day cat (junior on her own dashboard) renders as a newborn in every friend's visit overlay — violating §4.3's core promise that the tile/overlay shows the pet 'đúng growth stage thật', and quietly under-representing three weeks of real care.
- **Suggested fix:** Use 'junior' for cats in the 7–29 band (and consider mapping the as-built 5-stage scale — baby/kid/junior/teen/adult — rather than inventing a 3-stage vocabulary).

### [minor] Mailbox celebration repeats on every mount for stuck/unacked visits; gift-less visits get no friendVisit line
- **File:** src/components/dashboard/dashboard-client.tsx:225
- **Detail:** Two deviations from §4.2.1: (a) The collective toast fires whenever pending visits exist, but visits that could not apply (pantry + overflow both full → applied:false) and applied-but-ack-failed visits stay pending, so the same '1 bạn đã ghé thăm vườn 🌸' toast and friendVisit bubble replay on every reload/day until room frees — a gentle line turned into a nagging loop. (b) The friendVisit voice line is gated on giftApplied, so pure pet/cheer visits produce no pet storytelling at all, whereas the spec requires the no-gift variant for them ('visit chỉ pet/cheer dùng biến thể không quà') — the 🎁-only rule was meant to pick the variant, not suppress the event.
- **Suggested fix:** Track which visitIds have already been celebrated (e.g., persist last-toasted ids or only toast for visits newly applied this pass), and fire the friendVisit line for non-gift visits using the non-gift variants.

## Reviewer 2 — 11 findings

### [blocker] Milestones are client-authored, not server-diffed — fabricated content is published verbatim to friends
- **File:** supabase/schema.sql:1537
- **Detail:** Spec §4.1 requires refresh_my_summary to 'tự append milestones bằng cách diff với row trước (client không bao giờ cung cấp nội dung milestone)'. As built, refresh_my_summary copies profiles.milestones verbatim into the friend-visible published_summaries row (schema.sql:1537-1540, 1639). profiles.milestones (added at line 1335) is owner-writable via the existing 'Profiles are private' FOR ALL RLS policy (lines 90-92), so any user with a JWT can PATCH /rest/v1/profiles with arbitrary milestones — the validate_milestones trigger only constrains shape (10 items, 200 bytes, kind vocab), not truth or content. Failure scenario: attacker sets milestones=[{id:'x',kind:'streak',date:'2020-01-01',value:'365 ngày liền!'}], calls refresh_my_summary, and every friend sees a fabricated milestone chip and can cheer it. Additionally, NOTHING in the codebase ever legitimately writes profiles.milestones, so honest users can never earn a milestone — the feature only works for cheaters.
- **Suggested fix:** Implement the spec's server-side diff inside refresh_my_summary (compare newly derived stage/bond_tier/streak against the previous published row and append server-built milestone objects); drop profiles.milestones or revoke it from the owner-writable surface (column-level: move it out of profiles, or add a BEFORE UPDATE trigger rejecting client changes to it).

### [blocker] Gift-cap partial index `where applied_at is null` fails both ways: unlimited gifts after ack, and any second same-day action to a host hard-fails
- **File:** supabase/schema.sql:1483
- **Detail:** Spec §4.2 caps 1 gift per (visitor, host, visit_date) with `where (kind='gift')`. Built index garden_visits_one_gift_per_host_visitor_date uses `where applied_at is null` instead and there is no kind column. Under-enforcement: the moment the host applies+acks a gift (applied_at set — an online host does this within seconds via deliverGardenMailbox), the pending row leaves the index and the visitor can gift the SAME host again the same day, repeatedly — combined with the broken balance check (separate finding) this is a food pump; ack_garden_visits' 72h prune (lines 1857-1860) erases the history too. Over-enforcement: because every visit kind shares the index, a visitor who taps 'Vuốt ve' (row with gifted_food=0, applied_at null) can no longer gift or cheer that host the same day — the RPC's INSERT raises raw 23505, rolls back the food deduction, and the overlay shows the generic network toast (garden-visit-overlay.tsx handleGift falls to the final else). Verified there is no visit_garden-side count guard for gifts — only the index.
- **Suggested fix:** Add a kind/gift discriminator and index (visitor_user_id, host_user_id, visit_date) where gifted_food = 1 with NO applied_at predicate (cap must survive ack and prune of the current day); allow multiple non-gift pending rows or make pet visits recordless past the first.

### [blocker] Cheer unique index omits visitor_user_id — only the FIRST friend can ever cheer a milestone, and the overlay misreports the failure as success
- **File:** supabase/schema.sql:1487
- **Detail:** Spec §4.2: cap is 1 cheer per (visitor, host, milestoneId) — `on (visitor_id, host_id, (payload->>'milestoneId'))`. Built index garden_visits_one_cheer_per_milestone is on (host_user_id, cheered_milestone_id) only. Failure scenario: friend A cheers host's milestone M; friend B then taps the same chip → INSERT raises 23505 → garden-visit-overlay.tsx:200-202 matches /duplicate|unique/ against the raw error message and marks the milestone as cheered ('treat as done') — B believes their cheer landed but it never did. Also, because ack_garden_visits deletes applied rows after 72h, the '1 cheer per milestone ever' guarantee silently expires once the row is pruned, so the same visitor can re-cheer after 3 days.
- **Suggested fix:** Recreate the index as unique (visitor_user_id, host_user_id, cheered_milestone_id) where cheered_milestone_id is not null, exclude cheer rows from the 72h prune (or keep a separate durable cheer ledger), and have visit_garden catch unique_violation and return a typed 'already-cheered' status instead of leaking 23505.

### [blocker] visit_garden's food-balance check only counts TODAY's ledger — blocks legitimate gifts and mints food from raw-negative ledgers
- **File:** supabase/schema.sql:1749
- **Detail:** The check at lines 1749-1758 computes granted[today] + gifts[today] − spent[today], ignoring food_carryover and every prior day, and never clamps. This diverges from the canonical derivation clamp(carryover + Σgranted + Σgifts − Σ|spent|, 0, 21) used everywhere else (deriveFoodBalance, merge_companion_state). Failure 1 (false negative, breaks the core flow): user earns 3 food Monday, opens the overlay Tuesday with a full pantry visible in the UI → RPC raises 'insufficient-food' → toast tells them their basket is empty. Failure 2 (false positive, mints food): a client can push bogus spent-events via merge_companion_state so raw sum is −5 while displayed balance clamps to 0; earn 1 food today → today-net = +1 → gift passes → host receives a real +1 food while the visitor's displayed balance stays 0 → colluding accounts create food from nothing (spec gate: 'ping-pong gifting là net-zero'). Also v_overflow_bond_count (lines 1772-1776) is read and never used — dead code that suggests the overflow cap is enforced here when it is actually client-side.
- **Suggested fix:** Reproduce the full derivation in SQL (carryover + all granted days + all gift keys − all spent events, clamped 0..21) before deducting; delete the dead overflow read.

### [major] Projection leaks activity/miss data: last_refreshed and current_streak readable by friends, applied_at readable by visitor
- **File:** supabase/schema.sql:1353
- **Detail:** Spec invariant §0.3 (structural, not tonal): the projection must contain NO field allowing friends to infer miss days or inactive time — explicitly no last_active-like fields. Three leaks: (1) published_summaries.last_refreshed (line 1353) is selected by the friend RLS policy and returned by getFriendSummary — it is effectively 'when did this user last sync', i.e. last_active; (2) current_streak (line 1350) hitting 0 tells every friend the user missed yesterday+today — the spec's chosen fields (rhythm_score, weekly_good_days) avoid exactly this, and the overlay renders '🔥 N ngày liền tay' from it; (3) garden_visits.applied_at is visitor-SELECTable (policy line 1479-1480), so a visitor can poll their sent gift row and see the exact timestamp the host came online to absorb it. Failure scenario: friend watches last_refreshed/applied_at stall for a week → 'bạn ấy bỏ app rồi' — precisely the Strava-pressure failure mode the spec engineered out.
- **Suggested fix:** Drop last_refreshed and current_streak/best_streak from the friend-readable column set (or replace with the spec's rhythm_score/weekly_good_days computed to never expose zero-activity windows); restrict the visitor-side garden_visits SELECT to exclude applied_at (column-level grant or a visitor view).

### [major] visit_garden writes visitor's companion_meta without the 'betterme.companion' advisory lock — concurrent sync merge refunds the gift spend
- **File:** supabase/schema.sql:1698
- **Detail:** merge_companion_state serializes all companion_meta writes on pg_advisory_xact_lock('betterme.companion:'||uid) (line 593) and reset_companion does the same. visit_garden takes only the visitor-host pair lock ('betterme.visit:...', lines 1697-1700) before its read-modify-write of the visitor's food_spent_events (lines 1762-1770). Failure scenario: the visitor's background sync flush (markCompanionDirty debounce ~2s) starts merge_companion_state, which SELECTs the meta row; visit_garden commits the appended 'gift:' spend event; merge's UPDATE then overwrites food_spent_events with its pre-computed union that lacks the new event → the spend is erased → the visitor is silently refunded while the host still receives the gift → food duplication. The dashboard-client comment about mirroring via re-hydrate only covers the sequential case, not this interleaving. Same lock gap also lets two concurrent gifts to two different hosts both pass the balance check with 1 food (different pair locks).
- **Suggested fix:** In visit_garden, also take pg_advisory_xact_lock(hashtext('betterme.companion:' || v_visitor_uid::text)) before the balance check and ledger append.

### [major] Pet cap counts pending visits of ALL kinds across ALL hosts and resets on ack — wrong in both directions
- **File:** supabase/schema.sql:1733
- **Detail:** Spec §4.2: pet cap is 3 per HOST per day, counting pet actions, and over-cap must be silent (animation, no record). Built check (lines 1733-1741) counts garden_visits where visitor=me AND visit_date=today AND applied_at is null — no host filter, no kind filter, pending-only. Failure 1: a visitor who petted/gifted/cheered 3 different friends today gets 'pet-cap-reached' on EVERY further action to any host — including gifts and cheers (the check runs before them), and handleGift shows the generic network toast for that reason. Failure 2: because only pending rows count, once hosts ack, the count drops back to 0 and the visitor can pet-record without bound — the cap is whichever hosts are slow to come online. (The overlay does treat pet-cap-reached as a silent success for petting, but the server still rejects rather than 'animation without record', and gifts/cheers are collateral damage.)
- **Suggested fix:** Scope the count to (visitor, host, today) and to pet-kind rows only, drop the applied_at filter, and skip the check entirely when the call is gift/cheer-only.

### [major] Opt-out is not enforced at the data layer: no owner SELECT/DELETE on published_summaries, no profiles backstop trigger — a stale summary stays friend-visible after sharing is disabled
- **File:** supabase/schema.sql:1358
- **Detail:** Spec §4.1/§8: owner gets SELECT + DELETE ('DELETE giữ cho opt-out im lặng') and a profiles_propagate_summary AFTER UPDATE trigger backstops display_name/avatar/sharing changes. As built the ONLY policy on published_summaries is the friend SELECT (lines 1359-1368): the owner cannot read or delete their own row, and the policy never re-checks profiles.sharing_enabled. Row deletion happens solely inside refresh_my_summary when it observes sharing_enabled=false. Failure scenario: user flips profiles.sharing_enabled=false (direct PostgREST PATCH — allowed by the owner-ALL profiles policy — or any future settings UI whose follow-up refreshMySummary call fails on network; the client codebase calls refreshMySummary only fire-and-forget with silent failure); the published summary — name, pet, streak, milestones — remains readable by all friends indefinitely, and the user has no direct path to remove it. Same gap for display_name changes: update_my_profile (line 1259) deliberately does not hook refresh ('not done yet' comment at line 1332), so the server-side backstop the spec mandates does not exist.
- **Suggested fix:** Add owner SELECT/DELETE policies (auth.uid() = user_id); add `and exists (select 1 from profiles p where p.user_id = published_summaries.user_id and p.sharing_enabled)` to the friend SELECT policy; add the AFTER UPDATE OF display_name, avatar_kind, sharing_enabled trigger on profiles that updates/deletes the summary row.

### [minor] NULL-unsafe sharing checks: `if not v_host_sharing` passes when the host has no profiles row; refresh_my_summary publishes when its profile lookup finds nothing
- **File:** supabase/schema.sql:1718
- **Detail:** In plpgsql `if not NULL then` is false, so both guards fail-open. visit_garden (line 1718): if the host lacks a profiles row, v_host_sharing is NULL and the 'host-not-sharing' exception is skipped — the visit proceeds against a user who never opted in. refresh_my_summary (line 1542): with no profiles row, v_sharing_enabled is NULL, the opt-out branch is skipped, and the function INSERTs a published summary (null display_name, milestones coerced to []) for a user who never enabled sharing. ### [minor] refresh_my_summary invents its own stage/bond-tier scales instead of the as-built PET_STAGE_THRESHOLDS/BOND_TIER_THRESHOLDS — friends see the wrong pet
- **File:** supabase/schema.sql:1562
